# Project Structure and Development Workflow

How the AOH monorepo is organized, how local development works, and the development workflow conventions.

## Why

All services live in one Turborepo monorepo. This gives us atomic commits across service boundaries, shared tooling configuration, and a single CI entry point. No polyrepo gymnastics.

## Two monorepo shapes

AOH has **two** monorepo shapes in active use. Figure out which one you're in before applying conventions:

| Shape | Where | Tell-tale signs |
|---|---|---|
| **Consumer-app** | App teams' repos (the default historical shape) | Has `apps/<svc>/` + `packages/` + `compose/`. `go.work` points at `apps/`. No `modules/` directory. |
| **Ops-hub platform-monorepo** | `mssfoobar/ops-hub` (the platform itself) | Has flat root libs (`auth-sdk/`, `ui/`, `logger/`, etc.) + `modules/<name>/{web,client,types,service,deploy}/` + `apps/` + `tools/`. `go.work` points at `modules/*/service/`. `pnpm-workspace.yaml` globs `modules/*/*`. |

Rule of thumb: if you're modifying AGIL Ops Hub itself — the platform — you're in **ops-hub shape**. If you're modifying an app that *consumes* `@mssfoobar/*` packages, you're in **consumer-app shape**.

The sections below cover both. Skip the one that doesn't apply.

## Repository layout — consumer-app shape

- `apps/` — one directory per deployable service (Go backends, SvelteKit frontends)
- `packages/` — project-specific shared libraries reused across this repo's `apps/` (e.g., shared domain types, helpers)
- `compose/` — Docker Compose configuration for local development (one subdirectory per service, generated by the `aoh-compose` skill)
- `infra/` — non-compose infrastructure config (Keycloak realm configs, AAS seed files, etc.)
- `go.work` — Go workspace at the repo root, linking all Go modules under `apps/`
- Root-level `turbo.json` — Turbo task overrides per technology

## Repository layout — ops-hub platform-monorepo shape

The ops-hub repo holds the AOH platform: shared libs at the root, feature modules under `modules/`, dogfood apps under `apps/`, and CLI/tooling under `tools/`. A "module" is a vertically-sliced feature (e.g., GIS) — its own backend service, typed REST client, TypeScript types, Svelte SDK, and deployment artifacts, all colocated.

```
ops-hub/
├── auth-sdk/                      # Flat root libs — published to GitHub Packages
├── graphql/                       # one package each, no module nesting
├── logger/
├── sse-client/
├── ui/
├── modules/                       # Feature modules — vertically sliced
│   └── <name>/                    # e.g. modules/gis/
│       ├── web/                   # @mssfoobar/<name>-web-sdk — Svelte components, providers
│       ├── client/                # @mssfoobar/<name>-client — typed fetch wrapper
│       ├── types/                 # @mssfoobar/<name>-types — wire DTOs as TS
│       ├── service/               # Go backend (chi + sqlx + Viper + golangci-lint)
│       └── deploy/                # Dockerfile context, compose snippet, Helm skeletons
├── apps/                          # Reference apps that embed the modules
│   ├── reference-host/            # Production-shaped consumer
│   └── showcase/                  # Storybook + dev playground
├── tools/                         # CLI + module manifests
│   └── cli/                       # @mssfoobar/cli — installs modules into consumer apps
├── go.work                        # Go workspace covering all modules/*/service
├── pnpm-workspace.yaml            # Globs modules/*/{web,client,types,service} + apps/* + tools/*
├── turbo.json                     # Per-technology task graph
└── .golangci.yml                  # Shared lint config for all Go modules
```

### Workspace and Go-workspace globs

`pnpm-workspace.yaml` defines the canonical glob set:

```yaml
packages:
  - 'auth-sdk'
  - 'graphql'
  - 'logger'
  - 'sse-client'
  - 'ui'
  - 'modules/*/web'
  - 'modules/*/client'
  - 'modules/*/types'
  - 'modules/*/service'
  - 'apps/*'
  - 'tools/*'
```

Adding a new module under `modules/<name>/{web,client,types,service}` is picked up automatically — no `pnpm-workspace.yaml` edit needed.

`go.work` lists every `modules/*/service` directory explicitly. The `aoh-go-init` skill's `--target-dir modules/<name>/service` flag inserts new entries deterministically (and survived the substring-collision bug fixed in agent-skills #59).

### When to use each module sub-package

| Sub-package | Purpose | Built by |
|---|---|---|
| `service/` | The Go backend — chi router, sqlx, Viper, golangci-lint, swag-generated swagger | `aoh-go-init --target-dir modules/<name>/service` |
| `types/` | TypeScript mirrors of the wire DTOs from the Go service. Hand-authored — small surface, stable shape | Hand-authored or codegen from swagger (decision documented in the package) |
| `client/` | Thin typed `fetch` wrapper over the service's REST surface. Depends on `types/` via `workspace:*` | Hand-authored, tests via vitest mock fetch |
| `web/` | Svelte UI primitives + providers + stores for consumers. Depends on `client/` (and transitively `types/`) | `svelte-package`, storybook, vitest |
| `deploy/` | Composable artifacts for production: `compose.snippet.yml`, Helm skeletons, K8s manifests. Service Dockerfile lives at `service/Dockerfile` (next to its source) | Hand-maintained, references the service from the outside |

The dependency chain is one-way: `web → client → types → service` (and `service` doesn't depend on any of them — it's the runtime).

### Scaffolding a new module

Use the `aoh-module-init` skill. It scaffolds `modules/<name>/{web,client,types,deploy}` from templates, delegates `service/` to `aoh-go-init` with `--target-dir`, and confirms the workspace globs already cover the new path.

## Turborepo task configuration

Go services declare `inputs: ["**/*.go", "go.mod", ...]` and `outputs: ["bin/**"]`.
SvelteKit apps declare `outputs: ["build/**", ".svelte-kit/**"]`.

## Local development with Docker Compose

Every service ships with a Dockerfile. Local development runs through Docker Compose with Traefik as the reverse proxy.

- All services share a single Docker network (`name: aoh`)
- Traefik handles routing via labels — no hardcoded ports between services
- The `compose/` directory uses a compose-includes pattern: each service has its own `compose.yml`, and the top-level `compose.yml` includes them
- Dependencies are resolved transitively — Docker Compose deduplicates shared includes
- `compose.override.yml` (gitignored) handles developer-specific customizations like port mappings
- Environment variables are centralized in `.env` files with `.env.template` as the committed reference

## Naming conventions

- **App directories**: lowercase, hyphen-separated (e.g., `my-service`)
- **Go modules**: `github.com/org/repo/apps/{service-name}`
- **Docker images**: `ghcr.io/mssfoobar/<module>/<component>`
- **Image tag env vars**: `<MODULE>_<COMPONENT>_TAG=${GLOBAL_TAG}`

## Linting and formatting

Every service ships with pre-configured linting that must pass before code is considered complete.

- **Go**: `golangci-lint` with a shared `.golangci.yml` at the repo root. Rules include: no `panic`, no `time.Sleep` in application code, proper error wrapping.
- **SvelteKit**: ESLint (flat config) with TypeScript and Svelte plugins, plus Prettier with the Svelte plugin.

## Testing

Testing infrastructure is scaffolded alongside the service, not bolted on later.

- **Go**: `testify` for assertions, `mockery` for generating interface mocks. Tests use the `EXPECT()` pattern and table-driven structure.
- **SvelteKit**: Vitest for unit tests, Playwright for integration tests.

### Test-case design — equivalence partitioning + boundary-value analysis

Turning an OpenSpec `#### Scenario:` into tests is case *selection*, not transcription — derive the cases, don't guess them. Applies to Go (`testify` table tests) and SvelteKit (Vitest) alike.

- **Equivalence partitioning**: split each input/state into classes the code treats alike, and cover each class once. Always include the **invalid/unexpected** partitions (null, wrong type, out-of-domain, empty) — the ones most often skipped.
- **Boundary-value analysis**: for any ordered or bounded domain the bugs live at the edges — test `min`, `max`, and just-inside/just-outside each (`min-1`, `min`, `min+1` … `max+1`), plus empty / zero / overflow.
- One table row per class or boundary, **named for what it represents**, so a failure names the broken partition — not `case 7`.

Example — a `limit` query param valid for `1..100`: partitions `{<=0}`, `{1..100}`, `{>100}`, `{non-numeric}`; boundary rows `0, 1, 100, 101`.
